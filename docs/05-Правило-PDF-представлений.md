# Правило: представление схемы всегда имеет актуальный PDF

Этот документ — рабочий регламент, такой же обязательный, как
[правила оптимизации раскладки](03-Правила-оптимизации-схем.md).

---

## 1. Само правило

> **Любое изменение представления (View) в модели Archi обязано сопровождаться
> обновлением PDF-представления этого View в том же коммите.**

Изменением считается всё, что меняет схему: перекладка блоков и связей,
добавление или удаление элементов, переименование, смена цветов, свойств
(`Platform`, `Status`), подписей и легенд. Если после правки `.archimate`
PDF не перегенерирован — задача не закрыта.

Правило действует и в обратную сторону: PDF **не редактируется руками**.
Единственный источник истины — файл `.archimate`, PDF из него выгружается.

## 2. Имя и место файла

| Параметр | Значение |
|---|---|
| Каталог | папка проекта, та же, где лежит `.archimate` |
| Имя файла | `<проект>_<имя представления>.pdf` |
| `<проект>` | имя папки верхнего уровня (`CRM`, `Склады`, `Разделение ERP`, …) |
| `<имя представления>` | имя View, как оно задано в Archi, без изменений |

Примеры: `CRM/CRM_Целевое+.pdf`, `Склады/Склады_Целевая архитектура.pdf`,
`Единые сервисы/Единые сервисы_Календари.pdf`.

Если в проекте несколько моделей (как в `SRM`), имя проекта в префиксе остаётся
одно — различают представления их собственные имена. Символы, недопустимые в
имени файла (`/ \ : * ? " < > |`), заменяются на `-`.

## 3. Три способа выгрузки

### 3.1. Основной: Archi + плагин jArchi (вектор, текст остаётся текстом)

Рисует сам Archi, поэтому расхождений с тем, что видно на экране, нет.
Нужны установленный **Archi 5.x** и плагин **jArchi 1.7+** (в нём есть
`$.model.renderViewToPDF`); на Linux без графической сессии — `xvfb`.

```bash
tools/archi_export_views.sh                       # все модели репозитория
ARCHI=/opt/Archi/Archi tools/archi_export_views.sh   # если Archi не в PATH
```

Скрипт для каждой модели вызывает Archi в консольном режиме

```
Archi -application com.archimatetool.commandline.app -consoleLog -nosplash \
      --loadModel "<модель>.archimate" --script.runScript tools/export_views.js
```

и в конце сам выполняет `python3 tools/archi_export_pdf.py --adopt --renderer archi`,
то есть вносит выгруженные файлы в манифест.

Одну модель или один View удобно выгрузить прямо из Archi:
**File → Export → View As Image**, формат PDF, имя файла по правилу из п. 2,
затем `python3 tools/archi_export_pdf.py --adopt`.

Параметры выгрузки заданы в `tools/export_views.js` (`textAsShapes: false`,
`embedFonts: true` — текст остаётся текстом, шрифт кладётся внутрь PDF).
Если шрифта модели нет на машине выгрузки и подписи «плывут», в этом же файле
переключите `textAsShapes: true` — текст станет кривыми, вид будет точным.

### 3.2. Archi без плагина: картинка из HTML-отчёта

Собранный jArchi публично не раздаётся (его получают патроны проекта). Если
плагина нет, картинку всё равно рисует сам Archi — через HTML-отчёт, который
он умеет собирать из командной строки:

```bash
tools/archi_export_report.sh                       # все модели репозитория
ARCHI=/opt/Archi/Archi tools/archi_export_report.sh
```

Скрипт для каждой модели выполняет

```
Archi -application com.archimatetool.commandline.app -consoleLog -nosplash \
      --loadModel "<модель>.archimate" --html.createReport <каталог>
```

берёт из отчёта картинку каждого представления и оборачивает её в PDF
(`tools/archi_report_pdf.py`), после чего фиксирует файлы в манифесте с
пометкой `archi-report`.

Вид — ровно как в редакторе, но PDF растровый: текст в нём не выделяется и не
ищется. Это единственное отличие от способа 3.1.

### 3.3. Резервный: встроенный рендер репозитория

Когда Archi под рукой нет вовсе (чужая машина, быстрая проверка) —
`tools/archi_export_pdf.py` рисует схему сам, без единой внешней зависимости:
нужен только Python 3 и системный TrueType-шрифт с кириллицей (Liberation Sans
или DejaVu Sans находятся автоматически, иной путь — ключи `--font`/`--font-bold`).

```bash
python3 tools/archi_export_pdf.py                                   # все модели
python3 tools/archi_export_pdf.py "Склады/WMS.archimate"            # одна модель
python3 tools/archi_export_pdf.py "Склады/WMS.archimate" --view "Целевая архитектура"
python3 tools/archi_export_pdf.py --list                            # перечень файлов
```

Вывод: `+` — файл создан, `~` — обновлён, `=` — уже актуален. Полная выгрузка
всех 36 схем занимает меньше секунды.

Встроенный рендер **не перезаписывает** представления, выгруженные из Archi:
для них он сообщит, что нужен повторный экспорт (`tools/archi_export_views.sh`).
Перебить это поведение можно ключом `--force`.

Отличия резервного рендера от картинки Archi перечислены в п. 7.

## 4. Манифест и проверка перед коммитом

Файл `pdf-представления.json` в корне — реестр выгруженных представлений:
для каждого PDF хранятся отпечаток схемы на момент выгрузки, хеш самого PDF и
то, чем он нарисован (`archi` — jArchi, `archi-report` — картинка из отчёта
Archi, `python` — резервный рендер). Отпечаток считается по содержимому
представления (геометрия, стили, подписи, свойства, картинки), а не по картинке,
поэтому проверка одинаково работает для обоих способов выгрузки.

Манифест обновляют инструменты — руками его не правят.

```bash
python3 tools/archi_export_pdf.py --check
```

`--check` ничего не пишет на диск и сообщает обо всех расхождениях:

| Сообщение | Что произошло |
|---|---|
| `УСТАРЕЛО` | схему изменили, представление не перевыгрузили |
| `НЕТ ФАЙЛА` | у представления вообще нет PDF |
| `НЕ В РЕЕСТРЕ` | PDF есть, но его не зафиксировали (`--adopt`) |
| `ПРАВЛЕН РУКАМИ` | PDF заменили или отредактировали в обход выгрузки |
| `ЛИШНИЙ` | PDF остался от представления, которого больше нет (удалить руками) |

Чтобы правило соблюдалось автоматически, ставится git-хук:

```bash
git config core.hooksPath tools/hooks
```

Хук `tools/hooks/pre-commit` запускает `--check`, когда в коммит попадают файлы
`.archimate`, и не даёт закоммитить схему без обновлённого представления.

## 5. CI на GitHub

Workflow [`.github/workflows/pdf-representations.yml`](../.github/workflows/pdf-representations.yml)
формирует представления на раннере GitHub.

| Когда | Что делает |
|---|---|
| push с изменением `*.archimate` или `tools/**` | выгружает представления и коммитит их обратно в ветку |
| pull request | то же для веток этого репозитория; для форков — только проверка и артефакт |
| запуск вручную (**Actions → Представления схем (PDF) → Run workflow**) | перевыгрузка по требованию |

Порядок шагов на раннере:

1. ставятся `xvfb` и шрифт **Selawik** — открытый шрифт Microsoft, метрически
   совместимый с Segoe UI, которым размечены схемы (через `fontconfig` он
   подменяет Segoe UI, поэтому переносы строк в подписях совпадают с Archi);
2. скачивается Archi (ссылка определяется автоматически со страницы загрузки,
   дистрибутив кешируется между запусками);
3. выгрузка идёт по первому доступному способу:
   `tools/archi_export_views.sh` (jArchi, если задан `JARCHI_URL`) →
   `tools/archi_export_report.sh` (HTML-отчёт Archi) →
   `python3 tools/archi_export_pdf.py` (резервный рендер);
4. изменившиеся PDF и `pdf-представления.json` коммитятся от имени
   `github-actions[bot]` и выкладываются артефактом `pdf-представления`;
5. финальный `--check` обязан быть зелёным, в логе указан выбранный способ.

Ссылки задаются в **Settings → Secrets and variables → Actions**:

| Имя | Где | Зачем |
|---|---|---|
| `ARCHI_URL` | Variables | своя версия или сборка Archi (`Archi-Linux64-*.tgz`), если автоопределение не сработало |
| `JARCHI_URL` | Secrets или Variables | ссылка на jArchi (`*.archiplugin`/`*.zip`). Без неё CI идёт путём 3.2 — вид тот же, но PDF растровый |

Собранный jArchi публично не раздаётся, поэтому положите свою копию туда, куда
раннер может достучаться (релиз приватного репозитория, объектное хранилище,
подписанная ссылка), и укажите её в `JARCHI_URL`.

Когда Archi на раннере поднять не удалось вовсе, сборка не встаёт: включается
резервный рендер (п. 3.3). Представления, выгруженные из Archi, он не
перерисовывает — они будут отмечены как требующие повторного экспорта, и
финальная проверка сделает сборку красной. Это осознанное поведение: лучше
красная сборка, чем тихая подмена точной картинки резервной.

## 6. Что содержит PDF

Одно представление — одна страница, размер страницы равен размеру схемы,
ничего не обрезается.

| Способ | Что внутри |
|---|---|
| 3.1 jArchi | чистая схема Archi, вектор, текст ищется и копируется |
| 3.2 HTML-отчёт | чистая схема Archi, растровая картинка, текст не выделяется |
| 3.3 резервный рендер | схема плюс шапка (`<проект> — <имя представления>`, имя модели и путь к `.archimate`) и подвал с источником; вектор, текст ищется |

## 7. Отличия резервного рендера от Archi

Относятся только к способу 3.3; выгрузка силами Archi (3.1 и 3.2) этих отличий
не имеет.

| # | Отличие | Причина |
|---|---|---|
| О1 | Шрифт — системный (Liberation Sans / DejaVu Sans), а не Segoe UI | Segoe UI нет на Linux и в CI; метрики близкие, ширины блоков не меняются |
| О2 | Подпись, не влезающая в блок, уменьшается до 6.5 px, но не обрезается | В PDF важнее прочитать подпись, чем повторить обрезку Archi |
| О3 | Подписи связей ставятся в середину ломаной и подложены белым | Иначе подписи теряются на пересечениях линий |
| О4 | Связи между вложенным блоком и его родителем не рисуются | Так же ведёт себя Archi при вложении элементов |
| О5 | Фигуры и значки — по нотации ArchiMate, но не пиксель в пиксель как в Archi | Рендер свой; для точного соответствия используйте способ 3.1 или 3.2 |

## 8. Порядок работы

1. Правим представление в Archi, сохраняем `.archimate`.
2. Выгружаем представления: `tools/archi_export_views.sh`, без плагина —
   `tools/archi_export_report.sh`, без Archi — `python3 tools/archi_export_pdf.py`.
3. Смотрим метрики читаемости: `python3 tools/archi_metrics.py "<модель>"`.
4. `python3 tools/archi_export_pdf.py --check` — убеждаемся, что всё актуально.
5. Коммитим `.archimate`, PDF и `pdf-представления.json` **вместе**, одним коммитом.

Если Archi под рукой нет, можно закоммитить только изменённую схему: CI выгрузит
представления сам и добавит их в ту же ветку отдельным коммитом (п. 5).
